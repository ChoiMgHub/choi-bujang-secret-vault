# 11단계 · 설치 화면과 서버 기기 승인

## 구현과 신뢰 경계

기존 자료실에 manifest·이름·아이콘·설치 UI·공개 오프라인 안내를 추가했다. 앱 설치와 자료 접근 승인은 별개다. 서비스 워커는 `/offline.html` 한 파일만 저장하며 API·로그인 응답·메모를 저장하지 않는다.

기기 승인은 이 실습에서 **서버가 검증한 해당 브라우저의 로그인 세션에 대한 등록**으로 구현했다. Supabase SDK가 서명을 검증한 `session_id`와 검증된 사용자 ID를 묶어 16자리 확인 코드를 만든다. 원본 세션 ID·토큰은 화면이나 감사 기록에 반환하지 않는다. 기기 개인키를 발급하지 않으며 JS 저장소·IndexedDB·서비스 워커에 인증값을 저장하지 않는다. 기존 서버 전용 SDK와 Secure·HttpOnly·SameSite 쿠키 방식을 유지한다.

이는 물리 PC의 하드웨어 증명이나 복사된 세션 토큰을 구분하는 장치 인증은 아니다. 같은 브라우저라도 로그아웃 후 새로 로그인하거나 시크릿 창을 새로 만들면 새 승인이 필요하다. 새로고침·정상 토큰 갱신은 같은 세션 승인을 유지한다.

학생 앱의 API는 아래와 같다. 운영 엔진용 `aleph.decision.v1`에 새 필드를 추가하지 않는다. 기존 `createLoginVerifier` 소스와 판정기 5개 응답 필드·RULE_IDS는 보존했다. `permitsRegisteredDevice`의 엄격한 참값 규칙을 판정기와 서버 차단에서 함께 사용한다. 운영 릴레이의 별도 기기 승인 연동을 구현했다고 주장하지 않는다.

| 경로 | 수행하는 일 | 수행하지 않는 일 |
| --- | --- | --- |
| `GET /api/device` | 인증된 현재 세션의 DB 승인 상태 조회 | 요청 자동 생성·자동 승인 |
| `POST /api/device`, 본문 `{}` | 해당 세션의 `pending` 요청만 생성 | 클라이언트가 사용자·기기·승인 상태 선택 |
| 보호 메모·공지·강사·관리·복구 API | 매번 DB 승인 상태 확인 후 기존 소유자·강사 권한 검사 | UI 숨김만으로 접근 보호 |

학생 로그인에서 미승인·대기·철회·만료는 자료 없이 `403 DEVICE_APPROVAL_REQUIRED`, 승인 확인 실패는 자료 없이 `503 DEVICE_CHECK_UNAVAILABLE`다. 익명 요청은 기존처럼 401이다. 학생 발급자의 직접 Bearer 요청도 승인 검사를 건너뛰지 않는다. 화면은 초기부터 메모를 숨기고 승인을 확인한 뒤에만 불러온다. 오프라인·로그아웃·승인 철회 확인 시 메모 DOM과 편집 내용을 지운다. 승인 상태는 30초마다 다시 확인하며 모든 보호 API는 그보다 먼저 매 요청에서 확인한다.

## 기존 운영 서명 경로와 학생 브라우저의 구분

이 시작 틀의 `createLoginVerifier`는 학생 Supabase 토큰과 공식 심판의 ES256 토큰을 구분한다. 운영 릴레이의 신원·기기·경로 검사는 기존 계약상 앞단에서 수행된다. 공식 서명 검증을 통과한 심판 시험 신원에는 학생 DB의 Auth 세션이 없으므로 학생 등록표를 요구하지 않고 기존 서버의 소유자·강사 권한 검사를 계속 적용한다. 이는 브라우저가 보내는 역할이나 설치 상태로 선택하는 경로가 아니다.

최종 격리 서명 회귀 시험에서 수정 전 정상 요청의 503을 재현했고, 수정 후 자기 메모 200·타인 404, 위조 서명·잘못된 대상/역할 401, 심판 역할값을 덧붙인 미승인 학생 JWT 403을 확인했다. 기존 서명 검증기 소스는 바꾸지 않았다. 실제 운영 심판 토큰을 발급받아 실행한 결과나 새로운 운영 기기 승인 계약이 준비됐다는 주장은 아니다.

## DB 준비와 관리자 승인

1. 기존 프로젝트의 SQL Editor에서 [준비 SQL 전체](../sql/step11-device-approval.sql)를 `postgres`로 실행한다. 새 비공개 스키마·등록표·감사표와 제한된 함수 두 개만 추가한다. 기존 메모·계정·1~10단계 정책·감사 기록은 변경하지 않는다. 전제나 이름 충돌·권한 검증 실패 시 트랜잭션이 중단된다.
2. 마지막 결과는 `schema: aleph.device-setup.v1`, `ready: true`, `serverCanRequest: true`, `clientCanApprove: false`, `serverCanApprove: false`여야 한다. 실제 결과를 보기 전에는 준비 완료라고 기록하지 않는다.
3. DB 준비 확인 후 11단계 코드를 배포한다. A로 로그인하고 `기기 승인 요청`을 누른다. 요청 전·대기 상태에서는 메모가 없어야 한다. 이 시점에서 승인 대기와 비어 있는 자료 영역을 함께 캡처한다. 설치 여부는 승인 근거가 아니다.
4. 사용자가 자기 브라우저에 표시된 계정과 확인 코드 16자리를 대조한다. 관리자는 기존 SQL Editor에서 다음 문장을 실행한다. 확인 코드가 없거나 일치하지 않으면 실행하지 않는다. 코드 자리에 토큰·비밀번호를 넣지 않는다.

```sql
SELECT public.aleph_step11_review_device(
  'learner-a@example.com',
  '화면의_확인코드_16자리로_교체',
  true
) AS result;
```

5. `status: approved`와 동일한 `deviceId`를 확인한 뒤 브라우저의 `승인 결과 다시 확인`을 누른다. 서버가 재확인한 뒤에만 메모가 보여야 한다. 이 시점에서 승인 상태와 가상 메모 한 건을 함께 캡처한다. 토큰·비밀번호·쿠키 원문은 캡처하지 않는다.
6. 다른 계정이나 새 로그인은 승인 공유가 안 된다. B도 필요할 때 따로 요청하고 B 계정·확인 코드를 대조해 승인한다. 가장 최근 요청을 일괄 승인하지 않는다.
7. 철회 시험은 같은 관리자 함수의 마지막 값을 `false`로 실행한다. 다음 보호 API 요청부터 거부되고 화면 재확인에서도 메모가 사라져야 한다. 철회된 세션은 재요청으로 승인을 되살릴 수 없다. 새 로그인에서 새로 요청해야 한다. 정상 기기의 승인을 유지할 필요가 있으면 별도 연습 세션에서 철회 시험을 한다.

DB 함수의 실행 권한을 분리했다. `service_role`은 상태 조회·요청 함수만 실행한다. 관리자 승인 함수는 `postgres`만 실행한다. `anon`과 `authenticated`는 두 함수와 비공개 표에 직접 접근할 수 없다. 유효한 `auth.sessions` 행과 사용자·세션 조합도 DB에서 확인하며, 승인은 7일 후 만료된다. 요청·승인·철회는 별도 감사 이력에 추가한다. 준비 SQL 재실행은 등록 상태와 이력을 보존한다.

- 사용자: 변경 전 배포의 새 시크릿 창에서 A 로그인과 자기 가상 메모 정상 표시 확인.

- 자동 시험: `npm test` 131개 통과. UI 승인 대기·승인 후 로드·철회·실패·로그아웃 경합, 실제 서명 검증을 거친 메모 요청의 승인 전 거부와 승인 후 소유자 경계를 시험한다.
- 격리 PostgreSQL/WASM: 준비 SQL 전체 실행, 역할별 직접 접근, 관리자 승인, 계정·세션 분리, 재요청·재실행, 철회·만료, 사라진 세션, 다른 자료·감사 보존 12개 통과. 실제 Supabase 실행 결과가 아니다.
- `npm run build -- --local` 성공, `git diff --check` 오류 없음. 실제 DB 준비는 사용자 결과로 확인했다. 새 코드 배포와 공개/미로그인 HTTP 점검은 아래 기록처럼 확인했다. 브라우저 승인·실제 설치·오프라인/복귀는 위의 사용자 실측으로 확인했다. 심판 제출·판정은 미확인이다.
- `npm run verify:step11`은 배포 식별 정보·기존 미로그인 요청 20항목·PWA 파일·기기 함수 직접 호출 거부를 실측한다. 승인된 사용자 시험이나 브라우저 설치 완료로 기록하지 않는다.

## 완료와 제출

실제 준비·배포·정상/금지 확인 후 README의 미실행 항목을 관찰한 결과만으로 갱신한다. `aleph.config.json`은 11이며 기존 허용 경로와 발급자를 유지한다. 기기 신청은 자료용 허용 경로에 추가하지 않는다. 변경 파일·비밀값 검사를 확인하고 `11단계 저장점`으로 커밋한 뒤 `npm run bundle`을 실행한다. 첫 오류가 있으면 그 오류만 해결한다. 묶음 JSON은 저장소에 커밋하지 않는다.

## 배포 호환 보완

첫 11단계 배포는 실패했으며 그동안 10단계 주소는 유지됐다. 직접 빌드 로그는 Vercel 로그인이 필요해 읽지 못했다. 코드의 함수 수가 13개로 늘어나 Hobby 직접 함수 한도 12개와 충돌하는 것이 유력하다. 기존 `/api/ai`, `/api/threat-intel`의 미구현 501 응답을 `api/[feature].js`의 정확한 두 경로로 보존하고 함수 수를 12개로 줄였다. 쿼리로 기능을 선택하지 않고 다른 경로는 404다. API·승인 권한을 완화하지 않는다. 원인 확정과 배포 성공은 재배포 결과와 구분한다.

## 실제 공개 HTTP 확인
