# 12단계 · 제작 1, 서버 기록을 읽는 탈환 작전실

제작 1은 기존 Supabase 준비와 배포, 사용자의 실제 화면·API·DB 기록 대조를
완료했다. 이후 제작 2의 A·B 실측·DB 대조도 완료했으며, 제작 3의 재현 안내는
README에 정리했다. 최종 저장점 이후의 제출 묶음·심판 판정과 구분한다.

## 범위와 보존

기준은 `dc88ca91ada0e8453474ea20c26153544b727bcc`(11단계 저장점)이다.
기존 화면에 숨김 작전실 패널과 `/operations-ui.js`를 추가했다. 메모 패널의
승인된 표시 상태와 함께 열리고, 로그아웃·승인 확인 실패·오프라인에서는
요약과 늦은 응답을 버린다. UI 표시를 접근 권한으로 사용하지 않는다.

`GET /api/operations`는 기존 명시적 catch-all 함수에 연결해 배포 함수 수
12개를 유지한다. 기존 두 501 경로를 보존한다. 서버는 기존 로그인 검증과
세션 바인딩, 매 요청의 DB 승인을 확인한다. 요청으로 사용자·역할·기기·시험
성공을 지정할 수 없다. SQL도 유효한 사용자·세션과 승인을 다시 확인한다.
기존 판정기·탐지기·로그인 검증기·허용 경로·복구 실행 코드는 바꾸지 않았다.

## 기록의 출처

| 표시 | 출처와 범위 |
| --- | --- |
| 판정 규칙 | 서버가 가져온 실제 `RULE_IDS` 3개. 이 요약 조회 자체는 판정 시험을 실행하지 않음; 별도 요청표에서 가상 규칙 시험 |
| 탐지 사건 | 운영 엔진 사건·집계 연동은 미실행. 사건 수·제안 수는 null |
| 회수 | 현재 승인 세션에 한정한 DB 승인 철회 이력. 운영 엔진 회수 집행과 구분 |
| 복구 | 현재 사용자 소유의 기존 비공개 사본을 다시 읽어 SHA-256 검증. 현재 메모와의 비교와 기존 복구 감사 횟수만 조회. 복구를 새로 실행하지 않음 |
| 공식 41종 | 이번 총공세 결과를 받지 않았으므로 미실행, passed는 null |

메모 원문·제목·계정 UUID·세션 UUID·토큰은 응답과 서버 로그에 넣지 않는다.
A는 B의 사본 메타데이터나 복구 횟수를 읽지 못한다. 원본을 읽어 해시는
DB 내부에서 계산하지만 그 원문을 밖으로 반환하지 않는다.

새 SQL은 비공개 `aleph_operations_step12.snapshots`와 서버 전용 함수만
추가한다. 함수는 요약마다 DB 요청 ID·UTC 시각을 생성하고 현재 배포 커밋과
함께 저장한다. API·화면의 펼친 JSON·서버 가린 로그는 저장한 같은 객체다.
브라우저 역할과 서버 역할에는 이 표의 직접 권한이 없으며 서버만 제한
함수를 실행한다. 기존 메모·사본·승인·기존 감사표는 수정하지 않는다.

## 사용자가 실행할 DB 준비

1. 기존 프로젝트의 Supabase SQL Editor에서 새 쿼리를 연다.
2. `sql/step12-operations.sql` 파일 **전체**를 실행한다. 예상 결과 JSON은 SQL이 아니므로 입력하지 않는다.
3. 마지막 출력에서 `schema: aleph.operations-setup.v1`, `ready: true`,
   `clientCanRead: false`, `serverCanRead: true`를 확인한다. 사용자는 실제 실행
   결과에서 위 schema·ready·권한 세 값이 모두 일치하는 JSON을 제공했다.
4. 오류면 그 첫 오류를 기록하고 중단한다. 임의로 이전 사본을 만들거나
   승인 상태·기존 메모를 바꾸어 준비 성공을 꾸미지 않는다.
5. 새 배포 뒤 승인된 A·B에서 작전실을 열고 요청 ID·확인 시각·표시 값을
   JSON과 대조한다. API는 SQL이 없거나 응답 형식이 다르면 503이며 이전
   메모 기능을 변경하지 않는다. 사용자가 아래 기록의 제작 1 실제 브라우저·DB 대조를 완료했다.

현재 구성에 대한 새 실제 요청 검증과 공식 시험 결과는 별도다. 이 문서나
화면 문구를 12단계 통과·41종 공격 방어 증거로 사용하지 않는다.

## AI의 별도 검증 결과

- 첫 `npm test`: 기존 131개와 새 작전실 시험 6개, 총 137개 통과.
- `npm run build -- --local`: 성공. 실제 배포가 아니다.
- `git diff --check`: 오류 없음.
- 별도 PostgreSQL/WASM 엔진에서 기존 10·11단계 SQL과 새 SQL을 실행한
  시험 10개 통과. 계정별 사본 격리, 역할별 직접 호출 거부, 같은 감사
  객체의 저장·반환, 사본 훼손/현재 내용 불일치, 철회·만료와 재실행 시
  기존 자료·이력 보존을 확인했다. 실제 Supabase의 결과가 아니다.
- 위 항목은 제작 1 최초 준비본 시점의 시험이다. 이후 실제 배포·사용자 화면·DB
  대조는 아래 기록에 있다. SQL 준비 성공과 자료 접근 성공을 구분한다.

## 첫 배포의 경로 검사 보완

준비 SQL 확인 뒤 배포 `aa4a28d9236f2ffdf6e7a0ee0199e7eb99f7f566`을
기존 주소의 식별 API에서 대조했다. 작전실 HTML·스크립트는 200이었고
기존 익명 메모·기기·복구 거부는 401로 유지됐다. 새 작전실 GET은 최초
400 `INVALID_OPERATIONS_PATH`여서 성공으로 기록하지 않았다.

동적 `[feature]` 경로의 정확한 `feature=operations` 미러 값 한 항목만
받도록 보완했다. 다른 값·중복 값·사용자나 통과 수 같은 추가 선택자는
계속 거부한다. 이 일치/거부 회귀 시험을 추가해 작전실 시험 7개 통과를
확인했다. 이 보완의 실제 재배포 결과와 승인 사용자의 조회는 아직 미확인이다.

경로 보완 뒤 전체 `npm test`도 138개 모두 통과했다.
