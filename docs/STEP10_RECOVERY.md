# 10단계 · 백업에서 자료실을 되살리기

## 현재 진행 범위

사용자가 기존 Supabase에서 읽기 전용 SQL을 실행한 실제 정책 내보내기를 제공했다.
제작 1의 정책 사본·해시 재검증·시험 한 줄 변경과 제작 2의 시험 정책 복원을 완료했다.
운영 정책과 실제 메모는 변경하지 않았다. 제작 3의 비공개 사본 준비 SQL과 복구 API는 구현·모의 시험을 마쳤으며 실제 DB 적용과 배포는 대기 중이다.

사용자는 Chrome 새 시크릿 창에서 기존 B 연습계정으로 로그인하고,
복구 대상으로 사용할 가상 메모 **방어전 9단계 테스트**를 새로 만들었다.
사용자가 대상 ID·소유자·내용 해시를 조회해 한 건을 확인했다. 메모 사본의 실제 DB 보관은 아직 미실행이다.
대상 메모를 바꾸는 연습은 사본 검증 이후에 진행한다.

## 안전 정책 사본에 포함하는 범위

- 판정기와 연결된 기기·추가 확인·자원 구역 규칙의 소스 다섯 파일.
- 설정 전체 대신 `aleph.config.json`의 `allowedRoutes`만 별도 저장.
- 현재 DB 네 표의 RLS 설정, 정책, 표·열 권한과 일반·서버 역할의 실효 권한.
- 9단계 탐지 소스는 별도 회수 제안 규칙을 보존하기 위해 포함한다.

사본은 공개 정적 파일 폴더가 아닌 Git 제외 경로 `.private/step10-policy/`에 둔다.
메모 본문·계정·비밀번호·토큰·서버 키는 이 정책 내보내기 대상이 아니다.
각 파일과 매니페스트에 SHA-256을 계산한다. 해시는 지정한 사본과 일치하는지 검사하는 값이며,
변경 불가능한 외부 백업이나 전자서명 저장소를 구현한 것으로 표시하지 않는다.

## 실제 DB 상태를 먼저 읽기

기존 Supabase 프로젝트 SQL Editor에서 `sql/step10-read-policy-snapshot.sql`을 실행한다.
이 SQL은 시스템 목록만 읽는 SELECT 한 문장이며 표·메모·정책을 바꾸지 않는다.
결과의 `policy_snapshot` JSON 값을 내보내거나 복사한다. 이미지 대신 원본 JSON이 필요하다.
코드에 저장된 예전 SQL을 현재 DB의 실제 상태로 대신하지 않는다.

내보낸 JSON은 AI 작업 환경의 Git 제외 경로에 둔 뒤 다음 명령에 전달한다.

```bash
node scripts/policy-copy.mjs create .private/step10-db-policy-export.json
```

정책 사본에 들어갈 표 네 개와 필수 필드, RLS와 5·8단계 실효 권한을 먼저 검사한다.
필수 값이 없거나 일반 계정의 직접 접근 등이 남아 있으면 중단한다.
사본을 저장한 뒤 모든 파일을 다시 읽어 해시를 검증한다.
검증이 끝난 경우에만 시험용 사본의 기기 등록 조건 한 줄을 우회하도록 바꾼다.
실제 `src/decider.mjs`, 실제 설정과 DB는 바꾸지 않는다.

출력된 사본 ID와 매니페스트 해시를 사용해 차이만 확인한다.

```bash
node scripts/policy-copy.mjs preview <사본-ID> <기록한-매니페스트-SHA256>
```

정상 결과는 기준 커밋과 대상 `private_trial_only`, `src/decider.mjs`의 한 줄 차이다.
사본이 없거나 매니페스트·파일 해시가 다르면 차이를 보여 주기 전에 중단한다.
다른 경로와 감사 기록은 복원 대상으로 넣지 않는다.

## 실제 정책 사본과 시험 복원 결과

- 사용자 제공 DB 내보내기 SHA-256: `5ebaf2fbefe6770b1d7cd99def39fa5502cf8b0634411250b270485d417cf5e7`.
- 사본 기준 커밋: `17bc004a15e4aa2ee18208acd0529abcbdd36838`.
- 사본 매니페스트 SHA-256: `5de9256c40e83ce86296bd9247db3dc775f14248e9a472641a45140055c4b65b`.
- 실제 DB 네 표의 RLS가 켜져 있고, 일반 역할의 직접 접근은 제한돼 있다. 서버는 메모·공지 CRUD, 강사 자료·권한 표 읽기 권한이 있다. 메모의 소유자 정책 네 개도 확인했다.
- 시험용 `src/decider.mjs`의 기기 등록 조건 한 줄만 바뀐 것을 먼저 확인했다. 운영 파일·DB는 바꾸지 않았다.
- 사본 해시와 변경 계획 해시를 다시 확인해 시험 파일 한 줄만 복원했다. 기존 감사 기록 뒤에 복원 사건을 추가했다.
- 복원 뒤 사본과의 차이는 0개였다. 가상 요청은 등록 기기 allow 유지, 미등록 기기 allow에서 deny·device_not_registered로 돌아왔다.

```bash
node scripts/policy-copy.mjs restore <사본-ID> <기록한-매니페스트-SHA256> <직전에-확인한-planSha256>
```

변경 계획 뒤 시험 파일이 달라졌거나 시험에 없는 다른 항목이 바뀌었으면 복원하지 않는다.
실제 DB 정책은 읽어 보관했으며 운영 DB에 복원 SQL을 실행한 결과가 아니다.
B의 A 메모 접근 거부와 A의 정상 조회는 최종 배포 뒤 실제 계정 재시험에서 별도로 확인할 대상이다.

## B 메모 한 건의 대상 확인 · 다음 사용자 작업

기존 Supabase SQL Editor에서 `sql/step10-read-note-target.sql`을 실행한다.
공개 SQL의 `<B_ACCOUNT_EMAIL>`은 SQL Editor 안에서만 B 연습계정의 이메일로 바꾼다. 계정값을 채운 SQL은 Git에 올리지 않는다.
사용자가 선택한 B의 `방어전 9단계 테스트` 메모만 찾아 ID·소유자·내용 해시를 반환한다.
본문은 반환하지 않고 메모를 수정하지 않는다. 결과의 `matches`가 정확히 1이어야 한다.
0개나 여러 개이면 대상을 임의로 정하거나 변경하지 않고 먼저 확인한다.
이 조회를 실행했다고 비공개 메모 사본이나 메모 복구가 끝난 것으로 표시하지 않는다.

## 후속 단계 · 아직 미실행

- 제작 3 실제 적용: 비공개 사본 준비 SQL을 기존 DB에서 실행하고 반환된 준비 결과를 확인한다. 그다음 준비한 POST 경로를 배포해 실제 B 메모 한 건으로 시험한다.
- 제작 4: 이전 단계들의 정상·금지 요청 재확인 결과와 미실행 범위를 기록한다.
- README의 과거 판정 대기 문구는 이후 확인된 9단계 통과 사실로 갱신할 대상이다.

제작 1의 터미널 결과는 텍스트로 기록한다. 아직 화면 캡처를 요구할 단계는 아니다.

AI 환경의 모의 시험에서는 사본·매니페스트 해시 불일치와 파일 누락·예상 밖 파일에 대한 중단,
실제 소스·설정과 감사 기록 보존, 시험 사본 한 줄만 변경되는 조건을 확인한다.
모의 DB 정책 입력으로 통과한 결과를 실제 Supabase 내보내기나 실제 정책 복원 결과로 쓰지 않는다.

## 제작 3 · 지정 메모 복구 구현과 확인 범위

- 대상: 사용자가 지정한 B의 가상 메모 한 건. ID는 `ec10d0d2-ea65-42e8-97d3-2edc907e3943`이다. 소유자 UUID는 공개 코드·문서에 넣지 않는다.
- 서비스·경로: 기존 자료실의 서버 `POST /api/restore`, JSON 본문은 대상의 `id` 한 항목만 받는다.
- 사본: `aleph_recovery_step10` 비공개 스키마에 메모 원문을 DB 안에서만 복사한다. 브라우저·Git·제출 묶음으로 본문을 내보내지 않는다.
- `sql/step10-note-backup-and-restore.sql`은 세 매개값을 채워 기존 DB에서 실행한다. 사용자에게는 이미 확인한 값을 채운 비공개 실행본을 제공한다. 실제 소유자 값이 들어간 실행본은 Git에 올리지 않는다.
- 준비 SQL은 원래 메모와 기존 DB 정책을 바꾸지 않는다. 같은 이름의 다른 용도 객체가 있거나, 현재 원본의 ID·소유자·내용 해시가 달라졌으면 트랜잭션을 중단한다.
- 사본이 이미 있으면 덮어쓰지 않고 기존 사본의 ID·소유자·내용 해시를 다시 검사한다. 감사 이력도 지우지 않는다.
- API는 기존 로그인 검증 도우미를 그대로 사용한다. 소유자·역할·대체 내용을 요청 본문으로 받지 않는다. DB 복구 함수 실행 권한은 서버 역할에만 준다.
- 실제 복구 함수는 사본을 다시 해시로 검증하고 지정된 행만 쓰며, ID·소유자·내용 해시와 다른 메모 보존을 확인한 뒤 감사 사건을 추가한다. 복구 트랜잭션 중에는 짧게 메모 쓰기를 잠가 동시 변경을 구분한다.
- 단순 메모 변경뿐 아니라 대상이 삭제된 경우도 같은 ID·소유자·생성 시각으로 복구하는 조건을 모의 시험했다. 실제 현재 소유자가 달라졌다면 임의로 되찾지 않고 중단한다.

AI 환경에서 API 자동 시험 6가지와 격리된 PostgreSQL/WASM의 SQL 시험 13가지를 확인했다.
SQL 시험은 가상 메모·가상 사용자로 수행했으며 실제 Supabase 복구와 구분한다.
검사 명령은 다음과 같다. PGlite는 별도 시험 도구로 사용했고 실제 앱의 의존성에는 추가하지 않았다.

```bash
node --test test/restore-api.test.mjs
node scripts/check-step10-sql.mjs <별도로-설치한-PGlite의-dist/index.js-절대경로>
```

전체 자동 시험 실행에는 API 시험이 포함된다. 실제 사본 준비 결과가 확인되기 전에는 대상 메모를 변경·삭제하지 않는다.
