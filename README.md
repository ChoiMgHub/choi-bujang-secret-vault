사용자가 기존 Supabase SQL Editor에서 내보낸 실제 DB 정책을 검증하고, 규칙 소스·허용 경로를 포함한 정책 파일 7개의 사본을 만들었다.

운영 판정기·설정·자료 API·DB와 배포 버전은 기존 9단계를 유지한다.

## 현재: 9단계 · 도플갱어를 찾고 권한 회수를 제안합니다

`src/detect.mjs`에 같은 가명 사용자의 GET 조회가 어느 10분 구간에서든 120건을 넘을 때만 회수를 제안하는 `burst_read` 규칙을 구현했다. 사건 입력은 `at`, `method`, `identity.sub`만 읽는다. 기존 판정기·로그인·메모 소유자·구역 API·DB 권한과 화면은 보존했다.

### 입력과 시간 구간

- 입력은 `docs/DETECT_EVENTS.md`의 로컬 가상 사건 배열이다. 타임존이 있는 ISO 시각을 밀리초로 바꾸고, 사용자 식별값은 가명 sub를 그대로 사용한다. 네트워크·기기·지역·메모·토큰을 읽거나 만들어 넣지 않는다.
- 사건을 시각순으로 정렬하고 사용자별로 별도의 조회 창을 유지한다. GET만 센다. 고정된 시각 칸으로 나누지 않아 10분 경계를 걸쳐 몰리는 조회도 찾는다.
- 첫 사건과 마지막 사건의 차이가 정확히 600,000 ms이면 10분 구간에 포함하고, 그보다 큰 차이의 사건은 창에서 제외한다. 120건은 정상, 121건부터 회수 제안이다.
- 전체 묶음이 10분보다 길어도 내부의 어느 10분에 121건이 있으면 제안한다. 반대로 전체 200건이어도 각 10분에 120건 이하로 분산되면 관찰을 유지한다.
- 입력 순서나 현재 컴퓨터 시각을 판단 근거로 쓰지 않는다. 호출 사이에 사건을 누적하지 않으며 원본 입력을 수정하지 않는다. 여러 대상이 기준을 넘으면 시각순으로 처음 기준을 넘은 대상을 제안하고, 같은 시각은 가명 값 순서로 결정한다.
- 잘못된 배열·누락된 필수 값 등은 `invalid_detection_events` 또는 `invalid_detection_event`라는 고정 오류로 표시하며 입력 원문을 오류에 넣지 않는다.

### 정확한 반환값

정상 묶음은 다음 한 항목만 반환한다.

```json
{"action":"observe"}
```

의심 묶음은 다음 세 항목만 반환한다. subject는 실제 이름이나 기기 번호가 아니라 해당 사건의 가명 사용자 값이다.

```json
{"action":"propose_revocation","reasonCode":"burst_read","subject":"learner_fixture"}
```

이 결과는 회수 제안이다. 실제 계정·기기 권한을 변경하는 API나 실행 코드를 만들지 않았다. `src/decider.mjs`와 그 응답 형식·기존 RULE_IDS 세 개는 바꾸지 않았고, `burst_read`는 별도 탐지 함수의 이유 코드다.

사용자는 작업 전 Chrome 새 시크릿 창에서 A로 로그인해 자기 가상 메모가 보이는 것을 확인하고 로그아웃한 뒤, B에서도 자기 메모가 정상적으로 보인다고 확인했다. 이는 작업 전 정상 조회 근거다. 이번 단계에서 메모 생성·수정·삭제나 실제 회수 동작을 직접 수행한 것으로 확대하지 않는다. 코드·시험·GitHub·배포 점검은 AI가 지원했다. 9단계 구현 커밋 e120ce1이 실제 주소에 배포된 뒤에도 사용자가 A·B 모두 자기 가상 메모가 정상적으로 보이며 문제가 없다고 확인했다. 이는 배포 전후 정상 조회 확인이며, 실제 권한 회수 시험과 구분한다. 심판 제출·판정은 이 최종 기록 시점에 대기 중이다. 최종 기록 커밋은 README만 바꾸며 탐지·자료 API 코드는 사용자가 확인한 구현 커밋과 동일하다.

## 이전 8단계 · 자료마다 갈 수 있는 구역을 나눕니다

메모·반 공지·강사 자료의 자원 구분, 판정기의 구역 규칙, 최종 API의 권한 검사를 구현했다. 사용자는 2026-11-05 기존 Supabase 프로젝트의 SQL Editor에서 `sql/step08-resource-zones.sql`을 실행하고 권한 결과 9행의 캡처를 제공했다. 기존 메모·주소·화면 메뉴와 로그인 검증 도우미는 보존했다.

### 구현한 구역 경계

- 메모: 판정기는 GET·PUT·DELETE의 자료 ID 한 건 경로만 허용한다. ID 없는 목록·생성 경로, 예약 기능명 export·search·bulk·admin, 쿼리 선택자와 모르는 경로는 거부한다. 가상 ID를 UUID로 제한하지 않는다.
- 반 공지: 판정기와 공개 공지 API 모두 GET만 허용한다. 공지 쓰기는 강사라도 공개 경로에서 거부하며, 별도 `/api/admin/notices` 관리 경로에서 저장된 강사 권한을 확인한다.
- 강사 자료: 판정기는 모두 거부한다. 최종 API를 직접 호출해도 저장된 활성 강사 권한과 자료 소유자가 검증된 사용자와 일치해야 내용을 반환한다.
- 소유자·강사 역할은 클라이언트의 메뉴·본문·헤더에서 가져오지 않는다. 역할은 서버만 읽을 수 있는 `vault_resource_roles`에서 요청마다 확인한다. 일반 계정은 이 표를 읽거나 수정할 수 없고, 앱 서버 역할도 강사 역할을 새로 부여할 수 없다.

기존 브라우저의 자기 메모 목록·생성 기능은 로그인·소유자 검사 아래 유지한다. 이 관리 API와 판정기의 구역 허용 목록은 구분한다. 판정기 `allowedRoutes`에는 자료 ID를 지정한 메모 GET·PUT·DELETE와 공지 GET 두 경로만 기록하며, 강사 관리 경로는 넣지 않는다.

규칙 ID는 `resource_zone`, 구역 거부 이유는 `resource_not_allowed`다. 6단계 기기 규칙과 7단계 가상 복합 신호 규칙을 유지한다. 실제 운영 엔진의 등록부·중계 연결을 실측한 결과는 아니며, 운영 심판 수용 여부와 가상 시험을 구분한다.

### 새 DB 준비 범위

`sql/step08-resource-zones.sql`은 새 표 세 개만 만들고 민감정보가 없는 공개 실습 공지 한 건을 추가한다.

| 표 | 용도 | 앱 서버 권한 |
|---|---|---|
| vault_notices | 이 프로젝트의 반 공지 | 읽기·추가·수정·삭제 |
| vault_instructor_materials | 소유자가 있는 강사 자료 | 읽기만 |
| vault_resource_roles | 활성 강사 권한의 서버 기준 | 읽기만 |

새 표는 RLS를 켜고 PUBLIC·anon·authenticated의 직접 권한을 회수한다. 기존 `vault_notes`, 기존 메모 소유자, 로그인 사용자와 비밀번호, 앞 단계의 DB 정책은 변경하지 않는다. 강사 계정을 임의로 만들거나 A·B를 강사로 올리지 않는다. 초기 강사 권한 표와 강사 자료 표는 비어 있으며 실제 강사의 정상 관리 동작은 아직 실측하지 않았다.

같은 이름의 다른 용도 표가 있거나 상속 권한이 남으면 트랜잭션을 중단한다. 반복 적용은 공지를 중복 추가하거나 기존 내용을 덮어쓰지 않는다. SQL 마지막 결과는 표 3개 × 역할 3개의 권한 9행이며 RLS가 모두 true여야 한다.

### 현재 확인 범위

- 사용자가 변경 전 실제 자료실에서 A·B 각각 자기 메모 200 / 상대 메모 404를 확인하고 캡처 두 장을 제공했다. 이는 변경 전 단건 조회 확인이다.
- 별도 모의 API 시험에서 학생의 공지 읽기, 공지 쓰기 거부, 학생의 강사 자료·관리 경로 거부, 위조 역할·소유자 무시, 활성 강사의 관리 경로와 강사 자료 소유자 제한을 확인했다.
- 기존 기능을 포함한 자동 시험 81개가 통과했고 실패는 0개였다. 제공 판정기 가상 요청 13가지, 기존 7단계 정상·복합 사건, 로컬 정적 빌드도 통과했다. 가상 시험과 실제 배포 결과는 구분한다.
- 별도 PGlite 0.5.13 / PostgreSQL 18.6 시험 DB에서 SQL 적용·반복 적용, 기존 메모 보존, 일반 역할 거부, 서버의 역할 부여 금지, 상속 권한·같은 이름의 다른 표가 있을 때 변경 중단을 확인했다. 실제 Supabase 적용 결과와는 별개다.
- 첫 8단계 배포 뒤 사용자가 A로 로그인해 새 API를 직접 확인했다. 공지 쓰기와 강사 관리 요청은 403으로 거부됐지만, 단건 공지·강사 자료 읽기는 예상과 다른 400 QUERY_NOT_ALLOWED였다. 미로그인 HTTP 점검은 주소 검사 전에 반환되어 이 문제를 찾지 못했다. 최종 API에서 경로와 정확히 같은 ID 한 개의 중복 매개변수만 허용하도록 수정하고, 다른 ID·중복 ID·기능 선택자는 여전히 거부하는 회귀 시험을 추가했다. 수정 뒤 사용자가 A·B 각각 새 API를 재확인했고 공지 읽기는 200, 공지 쓰기는 403 NOTICE_READ_ONLY, 강사 자료·강사 관리는 각각 403 INSTRUCTOR_REQUIRED였다. A·B의 결과 캡처를 각각 제공했다.
- 실제 Supabase 권한 결과 9행에서 anon·authenticated의 새 표 읽기·추가·수정·삭제 권한이 모두 false, service_role의 공지 CRUD는 true, 강사 자료·권한 표는 읽기만 true, RLS는 전부 true인 것을 확인했다.
- 사용자는 수정 배포 뒤 A·B 모두 기존 상대 메모 조회 차단 확인에서도 자기 메모 200 / 상대 메모 404라고 확인했다. 이는 단건 읽기 확인이며 이번에 새로 메모 생성·수정·삭제까지 확인한 것으로 확장하지 않는다.
- 실제 HTTP 20개 항목과 제출 묶음 생성은 수정 배포 커밋 842545c에서 통과했다. 이 최종 기록 커밋은 README만 바꾸며 판정기·API 코드는 사용자가 확인한 수정 커밋과 동일하다. 최종 배포 커밋을 대조한 뒤 `npm run bundle`로 관측 결과를 갱신한다.
- 판정기·API 구현과 오류 수정은 AI가 지원했고, 사용자는 SQL 적용, A·B 실제 API·메모 확인, 오류 제보와 수정 후 재확인을 수행했다. 심판 제출·판정은 이 자체 확인에 포함하지 않는다.

## 이전 7단계 · 평소와 다른 접속은 다시 확인합니다

6단계의 `device_registered`를 유지하고 `step_up_required` 규칙을 추가했다. 엔진이 전달하는 계약 이름만 읽으며, 브라우저의 위치·네트워크·재확인 헤더를 근거로 사용하지 않는다. 기존 로그인·메모 소유자 검사·DB 권한과 화면은 보존했다.

### 입력 출처와 가상 사건의 기준

- `signals.source === 'judge_fixture'`: 지역·시각·네트워크, 최근 사건, 재확인 값의 형식을 검사한 뒤 가상 사건을 판정한다. 누락·잘못된 값·불명확한 출처는 정상값으로 채우지 않고 `step_up`으로 보낸다.
- `signals.source === 'none'`이고 지역·네트워크가 `unknown`: 제공 문서가 명시한 실제 경로의 정보 미제공 상태다. 가상 위험 신호로 승격하지 않고 6단계 기기 규칙만 적용한다. 이 경로에서 7단계 위험 분석이 수행됐다고 기록하지 않는다.
- 복합 조건은 가상 시험용으로 **0~5시 + unusual 네트워크 + 60초 이내 사건의 risk_signal count 20 이상**을 모두 요구한다. 이는 제공 fixture의 새벽 3시·낯선 네트워크·60초 전 count 20 신호를 처리하기 위한 규칙이며 실제 사용자의 평소 시간을 측정한 기준이 아니다. `risk_signal`의 count를 실제 서버에서 관찰한 자료 읽기 횟수라고 주장하지 않는다.
- 지역 값만 다르거나 복합 조건 중 일부만 있으면 차단하지 않는다. 이 단계의 추가 확인은 영구 차단이 아니라 `step_up`과 이유 코드 `step_up_required`로 요청한다.
- 기기 등록이 false이거나 누락되면 다른 조건이나 재확인 값과 관계없이 `deny`와 `device_not_registered`로 거부한다.

### 가상 재확인과 실제 재로그인의 확인 범위

`docs/DECIDER_REQUEST.md`에는 `stepUp: {verified, authAgeSeconds}`와 `step_up` 응답이 있다. 제공 연습기는 같은 가상 사건에 `verified: true, authAgeSeconds: 60`을 넣어 재확인 후 판정을 시험한다. 이번 가상 규칙은 verified가 실제 불리언 true이고 나이가 0~60초인 경우만 복합 사건을 허용한다. 문자열 true, 누락, 오래된 값은 허용 근거로 쓰지 않는다.

하지만 **이 저장소와 제공 문서에는 실제 재확인 요청과 같은 사용자의 새 로그인 시각을 결합해 검증하고, 자료 중계를 재개하는 실행 계약이 없다.** 실제 경로의 signals도 정보 미제공 상태다. 따라서 가상 재확인 값으로 실제 자료 차단이나 새 로그인 검증이 연결됐다고 기록하지 않는다.

| 확인한 상황 | 결과 | 확인 범위 |
|---|---|---|
| 등록 기기의 정상 가상 요청 | allow | 제공된 가상 요청 시험 |
| 미등록·기기 등록 값 누락 | deny · device_not_registered | 가상 요청 및 자동 시험 |

| 제공된 가상 사건의 유효한 재확인 값 | allow | 가상 값에 따른 재판정이며 실제 로그인 실측이 아님 |
| 지역 하나만 다른 사건 | allow | 자동 시험 |
| 재확인 전 판정기 응답 | 정해진 다섯 항목만 반환, 자료 필드 없음 | 가상 응답 형식 시험 |

새 작업 폴더에서 `npm install`을 실행했고 정상적으로 끝났다. `npm test`는 기존 로그인·쿠키·메모·소유자·배포 점검에 7단계 입력 출처, 누락·위조 값, 복합 조건의 경계, 가상 재확인과 기기 규칙 우선 적용 시험을 더해 **60개 통과, 실패 0개**였다. 실제 로그인 검증 도우미 `src/verify-login.mjs`는 변경하지 않았다.

### 100점 추가 구현: 로그인도 서버로 이동

브라우저는 같은 사이트의 `/api/auth`만 호출합니다. POST는 로그인, GET은 로그인 상태 확인과 필요 시 갱신, DELETE는 로그아웃입니다. 메모 자료의 allowedRoutes 다섯 경로는 유지하며 이 공개 인증 엔드포인트를 보호 자료 목록에 섞지 않습니다. 이메일·비밀번호 로그인과 갱신·현재 세션 로그아웃은 서버에서 설치된 공식 Supabase SDK로 처리합니다. 기존 SUPABASE_URL 설정을 쓰므로 새 키 입력은 필요하지 않습니다. 공개용 키는 서버 전용 모듈 `src/supabase-public.mjs`에만 두고 브라우저 파일이나 응답에 넣지 않습니다.

브라우저에는 사용자 ID·이메일·만료 시각만 반환합니다. Supabase가 발급한 접근·갱신 토큰은 Secure·HttpOnly·SameSite=Strict·호스트 전용 쿠키로 전달하고 JavaScript에서 읽거나 저장하지 않습니다. 서버는 상태 조회 시 getUser로 토큰을 확인하며, 갱신은 refreshSession으로 수행합니다. 메모 요청에서는 쿠키의 접근 토큰도 원본 `src/verify-login.mjs`로 검증하고 소유자를 제한합니다. 심판의 기존 Bearer 인증 경로는 유지합니다. 쿠키로 인증하는 쓰기 요청에는 동일 출처와 전용 요청 헤더 검사를 요구하고 인증 응답은 캐시하지 않습니다. ## 제작 3: 로그인한 계정의 메모 추가·조회·수정·삭제

브라우저의 내 가상 메모 양식과 카드의 수정·삭제 버튼을 연결했습니다. 수정 버튼은 단건 GET으로 최신 내용을 읽어 양식에 채우고 PUT으로 저장합니다. 삭제는 확인 후 DELETE로 처리하고 목록을 다시 조회합니다. 로그인 토큰은 SDK 세션에서 가져와 Authorization 헤더로 보내며 사용자 ID·소유자 ID를 브라우저에서 결정하지 않습니다. 저장 실패 시 초안을 보존하고, 로그아웃 시 메모와 초안을 지웁니다. 제목·본문은 textContent로 표시합니다.

| 실제 경로 | 요청·응답 계약 |
|---|---|
| GET /api/notes | 서버가 확인한 사용자 소유의 메모 배열 `[{id,title,body}]` |
| POST /api/notes | `{id?,title,body}` 입력. id는 UUID이며 생략하면 서버가 생성. 성공은 201과 `{id}` |
| GET /api/notes/:id | 단건 `{id,title,body}`. 없거나 삭제된 메모는 404 |
| PUT /api/notes/:id | `{title,body}`로 수정. 선택 id가 있으면 경로와 같아야 함. 성공은 단건 객체, 없으면 404 |
| DELETE /api/notes/:id | 성공은 `{id}`, 이후 같은 ID의 GET은 404 |

DB의 기존 content 열을 API의 body 필드에 대응시킵니다. 추가할 때 owner_id는 검증된 identity.userId로만 저장합니다. 클라이언트의 owner_id·userId·role은 소유자 지정에 사용하지 않고, 수정에서도 owner_id를 바꾸지 않습니다. POST는 insert이므로 같은 ID가 있으면 409이고 기존 자료를 덮어쓰지 않습니다. 잘못된 입력·UUID는 400, 큰 JSON은 413, 잘못된 인증은 자료 없이 401, DB 오류는 비밀값 없는 502입니다. 제목은 공백만으로 만들 수 없고 최대 200자, 본문은 최대 10,000자입니다.

3단계 당시 원래 네 메모는 owner_id가 NULL이었고 첫 로그인 계정에 자동 배정하지 않았습니다. 4단계 제작 1에서 사용자가 SQL을 직접 실행해 원래 네 건을 현재 A 계정에 연결하고 B의 가상 시험 메모 한 건을 추가했습니다. 메모 원문이 포함된 실행용 SQL은 공개 Git에 추가하지 않습니다.

3단계에서 사용자가 Supabase SQL Editor에서 서버 역할의 SELECT·INSERT·UPDATE·DELETE가 모두 true, RLS가 true, anon·authenticated의 SELECT가 false인 것을 확인했습니다. 같은 권한 설정은 `sql/step03-crud-permissions.sql`에 원문이나 비밀값 없이 보관했습니다. 제작 2까지는 이 DB 권한을 변경하지 않습니다. 4단계 제작 3에서 사용자가 authenticated의 최소 권한과 본인 행 RLS 정책 SQL을 직접 실행했고 안내한 권한 결과와 일치한다고 확인했습니다.

## 4단계 제작 2: 메모 API 소유자 검사

3단계의 단건 GET·PUT·DELETE에는 소유자 비교가 없었습니다. 변경 전 로컬 모의 DB 시험에서 B가 A의 ID를 지정해 읽기·수정·삭제할 수 있음을 다시 확인했습니다. 이는 실제 배포의 B 계정으로 수행한 시험이 아닙니다.

이제 목록과 단건 GET 모두 DB 조회에 `owner_id = identity.userId`를 넣습니다. PUT·DELETE도 ID와 검증된 소유자 ID를 같은 DB 문장의 조건으로 사용합니다. 변경 직전에 소유자가 달라져도 그 행은 수정·삭제 대상이 되지 않습니다. 다른 사람의 ID와 없는 ID는 모두 자료 없는 404 JSON `{ "error": "NOT_FOUND" }`로 응답합니다.

POST는 서버가 검증한 ID를 owner_id로 저장하며 클라이언트가 보낸 owner_id·userId·role을 소유자 지정에 사용하지 않습니다. PUT의 정상 본문은 `{title,body}`이고 owner_id 필드를 넣은 소유자 변경 요청은 400 JSON으로 거부합니다. 수정할 기존 행은 소유자 조건으로 제한하고 수정 후 소유자도 검증된 ID로 고정합니다. URL·헤더·본문의 사용자 주장은 권한 근거가 아닙니다.

내부 조회의 owner_id는 서버에서 확인한 뒤 제거하므로 단건 응답은 계속 `{id,title,body}`입니다. 목록도 같은 객체의 배열이고 삭제 응답은 `{id}`입니다. 예상과 달리 다른 계정의 행이 DB 응답에 섞여도 메모를 반환하지 않고 502 JSON 오류로 중단합니다. 서버 비밀키는 RLS를 우회할 수 있으므로 API 소유자 검사를 DB 정책으로 대체하지 않습니다.

자동 시험은 임시 서명 키·모의 Auth/DB를 사용해 A/B 각각의 정상 CRUD, 양방향 타인 및 소유자 미지정 메모 접근 거부, 소유자 변경 거부, 쓰기 직전 소유자 변경, 잘못된 DB 응답의 자료 차단을 확인합니다. 실제 DB의 RLS 동작이나 실제 A/B 배포 시험을 수행한 증거로 해석하지 않습니다.

이번 제작 2의 검증 환경에서 `npm test` 32개와 `npm run build -- --local`이 통과했습니다. 과거 3단계 점검 테스트는 현재 설정이 4단계로 바뀌어도 3단계 조건을 검증하도록 명시했습니다. 사용자 PC에서 이 명령을 실행했다고 기록하지 않습니다.

제작 2 배포 후 사용자는 먼저 로그아웃하고 현재 A 계정으로 새로 로그인합니다. 기존 네 카드가 보이는지 확인하고, 별도의 새 가상 연습 메모를 추가·수정·삭제합니다. A에서 로그아웃한 후 B로 로그인해 B의 한 카드만 보이는지 확인하고 같은 연습을 합니다. 원래 네 메모와 B의 고정 시험 메모는 삭제하지 않고 보존합니다. 목록 분리만으로 단건 API의 타인 접근 거부까지 확인됐다고 기록하지 않습니다.

사용자는 위 과정을 A·B 두 계정에서 모두 수행했고, 새로고침 후 삭제 유지까지 문제가 없다고 알려주었습니다. 이는 실제 배포에서의 정상 계정 사용과 목록 분리 확인입니다. 실제 계정 토큰으로 타인 ID를 지정한 단건 API 시험이나 직접 Data API의 authenticated 접근을 실행했다고 기록하지 않습니다.

## 4단계 제작 3: DB 최소 권한과 본인 행 RLS (사용자 적용 확인)

`sql/step04-owner-rls.sql`은 사용자가 기존 Supabase SQL Editor에서 검토하고 실행할 SQL입니다. `information_schema.role_table_grants`와 `has_table_privilege`로 적용 전후를 확인합니다. PUBLIC·anon·authenticated의 테이블 권한을 먼저 회수하고 authenticated에 SELECT·INSERT·UPDATE·DELETE만 부여합니다. SELECT·DELETE에는 기존 행 USING, INSERT에는 새 행 WITH CHECK, UPDATE에는 기존 행 USING과 새 행 WITH CHECK로 `(SELECT auth.uid()) = owner_id`를 적용합니다. 서버 역할의 기존 네 권한은 보존합니다. 메모 내용·소유자·계정·다른 테이블은 변경하지 않습니다.

기존 정책 중 이 단계에서 관리하는 네 정책 외의 것이 있거나 예상 밖의 상속 권한이 남으면 오류로 중단하고 트랜잭션을 되돌립니다. 기존 네 정책은 같은 정의로 다시 만들므로 반복 실행이 가능합니다. 마지막 결과는 anon의 네 권한이 false, authenticated의 네 권한이 true, 추가 권한 false, RLS true, 정책 수 4여야 합니다. 권한의 true는 모든 행 접근 허용을 뜻하지 않고 RLS가 본인 행으로 제한합니다.

AI의 별도 PGlite 0.5.13 PostgreSQL WASM 시험 환경에서 실제 SQL을 적용하고 반복 실행했습니다. 익명 CRUD 거부, A/B 각자 CRUD 허용, 타인 읽기·수정·삭제의 0행 결과, 타인/null 소유자 추가와 소유자 변경 거부, 기존 행 보존, 예상 밖의 정책·상속 권한에서 변경 중단을 확인했습니다. 시험의 auth.uid()는 로컬 요청 주체를 읽는 대역이며 실제 Supabase Auth나 사용자 DB를 시험한 결과가 아닙니다. 프로젝트의 런타임 의존성에는 시험 엔진을 추가하지 않았습니다.

사용자는 SQL Editor에서 이 SQL을 실행한 결과가 예상과 완전히 일치한다고 확인했습니다. anon의 CRUD false, authenticated의 CRUD true, 추가 권한 false, RLS true, 정책 수 4로 보고받았습니다. 이후 사용자는 새 시크릿 창에서 A/B 각각 메모 추가·수정·삭제와 새로고침 후 삭제 유지까지 다시 정상이라고 확인했습니다. 현재 서버 비밀키 경로는 RLS를 우회할 수 있으므로 앱 정상 동작만으로 authenticated의 직접 Data API RLS까지 검증했다고 주장하지 않습니다. 직접 Data API는 실제 배포 자기 점검에서 공개 키만 사용한 읽기가 HTTP 401과 권한 오류 42501로 거부되는 것을 확인했습니다. authenticated 역할의 직접 Data API는 실제 시험했다고 기록하지 않습니다.


## 4단계 마지막 확인과 제출 묶음

현재 자동 시험은 38개이며 모두 통과했고 로컬 정적 빌드도 통과했습니다. `src/verify-login.mjs`와 judgeIssuer는 원본을 유지합니다. allowedRoutes는 실제 GET 목록·단건, POST, PUT, DELETE 다섯 경로와 일치합니다. src/decider.mjs의 starter.deny는 시작 틀의 실제 기본 거부 규칙이며 이후 단계의 ZTNA/XDR 규칙을 구현했다고 기록하지 않습니다.

로그인 화면의 내 가상 메모 아래에서 **4단계 접근 확인 → 상대 메모 조회 차단 확인**을 누릅니다. 현재 계정의 고정 시험 메모가 200으로 읽히는지 먼저 확인하고 상대 계정의 시험 메모를 GET으로만 요청합니다. 자료 없는 404 NOT_FOUND JSON이어야 확인 완료로 표시합니다. 양쪽 계정에서 각각 실행해 각 시험 메모가 존재하는 상태의 양방향 거부를 확인합니다. 현재 계정의 시험 메모가 없거나 상대 메모 응답이 HTML·자료·다른 오류이면 성공이라고 표시하지 않습니다. 상대 시험 메모의 존재는 상대 계정의 정상 조회까지 함께 확인해 대조합니다. 이 버튼은 메모 추가·수정·삭제나 소유자 변경을 시험하지 않습니다. 토큰·메모 본문은 결과에 표시하지 않으며 로그아웃 시 결과를 지우고 늦은 응답을 무시합니다. 사용자는 실제 배포에서 A/B 두 계정 모두 버튼을 실행했고 내 메모 조회 200 / 상대 메모 조회 404(접근 거부)가 안내대로 나왔다고 확인했습니다. 이로써 두 고정 시험 메모가 각각 존재하는 상태에서 양방향 단건 읽기 거부를 확인했습니다. 실제 계정으로 타인 PUT·DELETE나 소유자 변경을 추가 실행했다고 주장하지 않으며 해당 거부는 모의 서명 API 시험과 별도 PostgreSQL RLS 시험으로 구분합니다.

`npm run verify:step4`는 실제 HTTP 요청으로 첫 화면, 보안 헤더, 정적 원문 부재, 4단계·저장소·커밋·발급자 정보, 익명 CRUD 및 잘못된 토큰 거부, 직접 Data API의 익명 읽기 거부 등 11개를 확인합니다. 직접 Data API에는 브라우저와 동일한 공개 publishable key만 사용하고 사용자 JWT나 서버 비밀키를 사용하지 않습니다. 401/403 JSON의 PostgreSQL 권한 오류 42501을 확인하므로 잘못된 키나 HTML 오류를 성공으로 해석하지 않습니다. 결과는 상태·참거짓과 고정 설명만 artifacts/step4-verification.json에 저장합니다. authenticated의 직접 Data API 시험은 포함하지 않습니다.

이 단계의 `npm run bundle`도 위 실제 HTTP 점검을 사용합니다. 4단계 저장점 커밋과 배포 커밋이 같고 자기 점검을 통과해야 artifacts/submission.json을 만듭니다. bundle-notes.json에는 사용자가 확인한 내용과 아직 확인 전인 내용을 구분합니다. 두 JSON과 artifacts/는 Git에 올리지 않습니다. 자기 점검 및 묶음 생성은 포털 심판의 통과나 100점 판정이 아닙니다. 사용자의 RLS 적용 후 A/B 화면·버튼 확인을 마쳤습니다. 이번 최종 기록 커밋의 배포가 반영된 뒤 묶음을 다시 생성하고 같은 배포 주소로 제출합니다. 포털의 실제 통과·점수는 제출 뒤 별도로 확인합니다.

## 배포·재현

같은 Supabase DB와 Vercel 프로젝트를 계속 사용합니다. 배포·빌드가 기존 메모를 초기화하거나 계정 소유자로 재배정하지 않습니다. 실제 사용자가 추가·수정·삭제를 누르면 해당 작업이 DB에 반영됩니다. Production 환경변수는 기존 두 개를 유지합니다.

| 이름 | 용도 | Vercel 유형 |
|---|---|---|
| SUPABASE_URL | 위 Supabase 프로젝트의 주소 | Config |
| SUPABASE_SECRET_KEY | 서버 전용 Secret key | Secret |

Node.js 22 이상(현재 사용 환경 24)에서 npm ci 후 npm test로 자동 시험을 실행합니다. npm run build -- --local은 로컬 정적 빌드이고 배포 식별 파일을 만들지 않습니다. 운영 빌드는 Vercel의 저장소·커밋·배포 URL 시스템 환경변수를 검증해 `/aleph.json`을 생성합니다. GitHub main의 변경은 기존 Vercel 프로젝트에 자동 배포됩니다. 환경변수 변경은 새 배포에 반영됩니다.

## 이전 3단계 제작 3 배포 후 사용자 확인

사용자가 안내한 순서로 실제 배포를 시험한 뒤 로그인과 메모 추가·수정·삭제가 모두 정상이라고 알려주었습니다. 아래는 재현 순서입니다. 자동 시험 결과와 사용자 확인은 구분하며, 비밀번호나 토큰은 전달받지 않았습니다.

1. 새 시크릿 창의 첫 화면 → 로그인 양식만 보이고 메모 양식·목록은 숨김. 익명 `/api/notes`는 401 JSON 오류.
2. A 로그인 → 내 가상 메모 양식과 A의 목록. 처음에는 빈 목록일 수 있음.
3. 새 가상 메모 추가 → 카드 표시 → 새로고침 후 유지.
4. 카드의 수정 → 제목·내용 변경 → 수정 저장 → 새로고침 후 변경 유지.
5. 카드 삭제 확인 → 목록에서 사라짐 → 새로고침 후에도 없음. API 시험에서는 삭제한 ID의 GET이 404인지도 확인.
6. 로그아웃 → 메모 양식·목록·초안 제거. 새로고침 후에도 숨김.

자동 시험은 임시 서명 키·모의 Auth/DB 응답을 사용합니다. 실제 사용자 비밀번호나 토큰을 받은 것으로 기록하지 않습니다. 시험은 서명 검증·익명/위조 거부·검증된 ID의 소유자 저장·계정별 목록·UUID 생성과 중복 거부·CRUD 형식·삭제 후 404·입력 검증·소유자 검사·SDK 로그인·화면 CRUD·로그아웃 후 늦은 응답 차단을 확인합니다.

## 이전 3단계의 제출 자기 점검과 묶음

`npm run verify:step3`는 3단계 당시의 배포에 익명·잘못된 토큰 요청을 보내 목록/단건/쓰기 거부와 배포 정보를 검사합니다. 임의의 사용하지 않은 UUID를 사용하고 쓰기 본문이나 로그인 자격 증명을 보내지 않습니다. 결과는 `artifacts/step3-verification.json`에 상태와 판정만 저장합니다. **이 점검은 실제 A 계정의 CRUD를 자동 확인한 증거가 아닙니다.** A의 브라우저 작업과 포털 심판 판정은 별도로 확인합니다.

위 명령은 step 3 배포를 전제로 한 과거 단계용입니다. 4단계에는 위의 verify:step4 및 갱신한 bundle 점검을 사용합니다. 현재 제작 2만으로 4단계 제출 준비가 끝났다고 기록하지 않습니다. 3단계에서는 실제 A의 CRUD 확인 후 Git에 올리지 않는 bundle-notes.json에 수행 내용과 남은 허점을 적고 `npm run bundle`을 실행했습니다. 깨끗한 작업 폴더의 현재 커밋과 배포 커밋이 일치하고 실제 HTTP 자기 점검이 통과해야 `artifacts/submission.json`이 만들어집니다. 본문·비밀번호·토큰·서버 비밀키는 묶음에 포함하지 않습니다. 자기 점검 통과와 파일 생성이 포털 심판 통과를 뜻하지는 않습니다.

## 2단계에서 보존한 결과와 과거 이력의 한계

2단계에서 메모 네 건을 Supabase `public.vault_notes`로 옮겼습니다. id uuid, owner_id uuid(NULL 허용·auth.users 외래키 없음), title text, content text, created_at timestamptz로 구성했습니다. RLS를 켜고 PUBLIC·anon·authenticated의 테이블 권한을 회수했으며 서버 역할에는 SELECT를 부여했습니다. 사용자가 SQL Editor 실행 결과에서 메모 4건, RLS true, owner_id uuid, 일반 역할 SELECT false, 서버 SELECT true를 확인했습니다. 시드 실행용 SQL은 원문이 있어 공개 Git에 올리지 않았습니다.

최신 루트 data.json은 빈 목록이고 public/data.json은 빌드 때 잔여 파일까지 제거합니다. 2단계의 익명 조회 자기 점검 `npm run verify:step2`는 당시 동작을 확인하는 과거 단계용이며, 3단계 인증 적용 뒤에는 같은 공개 조회 결과를 기대하면 안 됩니다.

최신 소스의 원문 제거가 과거 노출까지 지웠다는 뜻은 아닙니다. 1단계 공개 커밋과 옛 배포에는 메모가 남을 수 있고, 이력을 삭제하거나 다시 작성하지 않았습니다. 실제 키가 노출된 경우에는 폐기·교체와 과거 이력·배포 정리가 별도로 필요합니다.

PowerShell에서 최신 소스와 정적 결과물의 기존 시드 문장 형식을 확인합니다. 일치 결과가 없어야 하며 git grep 종료 코드 1은 일치 항목 없음입니다.

```powershell
git grep -n -E '실습용[[:space:]]+가상[[:space:]]+.{1,30}[[:space:]]+기록' -- .
Get-ChildItem .\public -File -Recurse | Select-String -Pattern '실습용\s+가상\s+.{1,30}\s+기록'
```

`.env*`, `.private/`, 비공개 시드 SQL, bundle-notes.json, artifacts/는 커밋하지 않습니다. 서버 소스에 환경변수 이름이 있는 것은 실제 키 값의 노출과 다릅니다. 판정기에는 6단계 기기 규칙과 7단계 가상 사건 추가 확인 규칙을 구현했습니다. 탐지기와 AI/침해 정보 API 등 남은 미구현 뼈대는 완성된 기능이라고 표시하지 않습니다.
